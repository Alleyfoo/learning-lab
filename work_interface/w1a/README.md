# W1-A test pack

**Status:** prepared, not executed. Goose has **not** been run. The pack is ready for
five fresh desktop Goose sessions (A1–A5). Do not modify the skill, the fixtures, or
the human-answer script between A1 and A5.

**Purpose:** the W0D boundary experiment showed the *validator* works — it refuses the
prose-shaped W0B artifact and passes a structural Work Definition that strips cleanly
into the existing floor. The open question is whether a `define-lab-process` skill that
**teaches the v0 structural contract** can reliably get a local model to *produce* that
structural form from an ordinary conversation. W1-A answers that for the
reconciliation family, five times, with the human input held constant.

This is still a **boundary/skill experiment**. It does not build a Goose API, MCP,
transport, model escalation, automatic establishment, or production file movement.
The W0D stop condition still holds.

### Reuse of the W0 reconciliation case

The fixtures are byte-copies of `work_interface/evidence/W0B_fixtures/`. This is
deliberate: the W0D validator's `observed_fields` cross-check is honest against these
exact headers, and `work_interface/cases/W0B_corrected.json` is the known-good oracle
for what a clean run should resemble. The human-answer script is derived from that
oracle's `human_confirmations`, so a perfect run reproduces the oracle. There was no
concrete reason to invent a new case.

## The frozen revision of define-lab-process

The prose-era skill (the one that produced the W0B artifact) is replaced. The frozen
revision at `skill/skill.md` teaches the **Work Definition v0 structural contract**
explicitly:

- the exact JSON envelope + reconciliation-body shape (with `«…»` placeholders, not answers);
- the closed vocabularies (`task_family`, `comparison`, `output_order`,
  `on_duplicate_key`, `on_non_numeric`, `basis`);
- the evidence/authority rules (`observed_fields` copied verbatim from the header;
  one scalar `basis` per decision; executable choices need `observed`/`human_confirmed`;
  `human_confirmed` needs a recorded confirmation; output names only declared fields);
- the authority invariant (`requested_authority: null`; no `established`/`approved`/
  `validation_override`/…).

The skill teaches the **contract**, not the **answers**. The answers live in
`human_answers.md`, so the human input — not the skill — is the controlled variable.

The same bytes are written to the live `skills/define-lab-process/skill.md` so a
desktop Goose session can `load_skill("define-lab-process")`. The grader records
whether the live skill still matches the frozen sha256; if it drifts, every run is
marked CONTESTED.

## How to run one session (A1–A5)

Follow `human_answers.md` exactly. Summary of the protocol:

1. Confirm the live skill matches the frozen revision (`skill/PROVENANCE.md`).
2. Copy the two frozen fixtures into the run directory `runs/A<i>/`.
3. Start the Goose session with the working directory set to `runs/A<i>/`.
4. Send the opening prompt from `human_answers.md`, load the skill, and answer its
   questions from the table. Do not correct the agent. Do not repair its artifact.
5. Confirm `runs/A<i>/work_definition.json` exists (if Goose wrote it elsewhere, that
   is a recorded defect — do not move the file).
6. Optionally drop a one-line `operator_notes.md` in the run dir for any protocol
   deviations.

Repeat, unmodified, for all five runs. **Do not edit the skill, the fixtures, or the
human-answer script between runs.**

## How to grade

```
python work_interface/w1a/grade.py
```

The grader reads each `runs/A<i>/work_definition.json` (read-only — it never edits,
repairs, renames, or moves an agent artifact), validates it with the existing W0D
validator (`work_interface/work_definition.py`), and writes `RESULTS.md` +
`RESULTS.json`.

### What the summary records

Per run:

| status | meaning |
|---|---|
| `PASS` | the W0D validator returned zero problems. Safe to enter the existing modelling/preview path. **Not established.** |
| `REFUSED` | the validator returned named refusal codes (sorted) + per-problem detail. The agent's structural form is not yet honest. |
| `NO_ARTIFACT` | no `work_definition.json` in the run directory (Goose did not write one, or wrote it elsewhere). |
| `UNPARSEABLE_JSON` | the agent produced a file that is not valid JSON (the validator never raises; this is a grader-level observation recorded before validation). |
| `CONTESTED_SKILL` | (pack-level, not per-run) the live skill no longer matches the frozen revision; results are from a different skill and must be discarded. |

Plus, for each run: the sha256 of the agent's `work_definition.json` (provenance —
detects later "repairs"), the `requested_authority` value, and any self-authorization
override keys present. The grader does **not** change or repair the agent output; a
bad run is recorded as bad.

## Rubric — what W1-A is graded on

The headline question: **does the skill reliably elicit the structural form?** Five
runs, one skill, constant human input.

- **PASS rate.** How many of A1–A5 are PASS? One pass is weak evidence; five is the
  target. The *distribution* of refusal codes across the refused runs is the real
  signal — it tells us whether the skill's weaknesses are systematic (the same code
  fires repeatedly) or incidental (different defects each time).
- **Structural vs prose.** A run that is REFUSED for `match_key_not_declared`,
  `malformed_sources`, `unknown_task_family`, or `unknown_work_definition_version` is
  a run where the agent still produced the *prose shape* the W0B run did — i.e. the
  skill did not move the agent to the structural form. A run refused only for
  narrower codes (`observed_field_not_in_source`, `output_field_not_declared`,
  `confirmation_missing`, …) is a run where the agent adopted the structural form but
  made a local error.
- **Authority invariant.** Any run carrying `requested_authority` other than null, or
  any override key, fails `authority_requested`/`prose_override_attempt`. This is the
  W2 property; it must never pass.
- **Oracle similarity (informational, not gating).** A PASS run may be compared to
  `work_interface/cases/W0B_corrected.json` by `sha256` / structural diff. Exact
  equality is not required and not expected (the agent picks its own `model_id`,
  prose `purpose`, etc.); what matters is that the *executable semantics* (match_on,
  compare, classify, policies) and the *basis/authority structure* match the oracle.
- **Provenance.** Each run's sha256 is recorded. If a run's sha256 changes between
  the session and the grade, someone edited the artifact — the run is invalid.

## Stop condition for W1-A

W1-A is **complete** when all five runs have been executed and graded, and
`RESULTS.md` records the PASS/refusal distribution. Do not, during W1-A:
- modify the skill (would invalidate the controlled-skill premise);
- repair any agent artifact (would falsify the measurement);
- proceed to transport, MCP, model escalation, establishment, or W1-B/C — those are
  later experiments, and only if W1-A's distribution justifies them.
