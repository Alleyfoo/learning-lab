# Handoff — Workspace v0.4 (declared XLSX materialization + durable source provenance)

## What was completed

**v0.4 — the workbook-ingestion vertical slice.** Removed the lab assumption
"someone already turned the company's files into modeller-ready collections."
An unfamiliar XLSX in the incoming browser now carries a "Define work" button;
the operator discovers its sheets (no LLM), declares sheet → collection +
header_row (operator authority — the program never decides which sheets have
business meaning), the existing XLSX adapter validates each declaration and
REFUSES (before any LLM call) any sheet it cannot faithfully convert, the valid
selections materialize into `data/_derived/<dir>/` (raw workbooks untouched), and
the UNCHANGED v0.3 modeller journey runs over the derived JSON. Each established
source binding carries durable `origin` provenance (workbook + sheet +
header_row) back to the exact company workbook.

**Crisp claim (user, verbatim, now proven):** "An unfamiliar workbook can enter
the product through an explicit, refusal-safe declaration, become deterministic
model input, and retain a machine-readable chain back to the exact company
workbook and sheet it came from."

### The three frozen design decisions (held)

1. Raw workbook stays immutable; materialization goes to `data/_derived/<ws>/`;
   the worker's `trigger` points at the RAW dir (NOT `_derived/`) so
   `incoming._link_worker` links the raw incoming workbook dir to the worker.
2. `header_row` is operator authority (the program shows a preview so the
   operator can confirm, but never sets it).
3. Adapter refusal happens before any LLM call (validate → REFUSE-and-stop-here
   → materialize → unchanged v0.3 modeller).

### The provenance semantic split (held, proven on disk)

`path` says what the worker executes (`_derived/<ws>/<file>.json`, read by
`load_collection`); `origin` says where that executable representation came from
(`{kind:"xlsx", path:"<raw_rel>/<workbook>", sheet, header_row}`). `origin` is
injected in the glue AFTER `propose` (which overwrites `sources` from
`source_spec`, path/collection only) and BEFORE `fleet.establish` (which writes
the model VERBATIM, so `origin` reaches `v1.json`). The executor never reads
`origin`; only the on-disk model + the map do.

## Known issues or failing tests

None. All self-tests PASS, py_compile OK, AppTest 0 exceptions, the real
acceptance run succeeded end-to-end on the model.

Honest nuances (not failures):
- The LLM chose `comparison:"exact"` for Amount (as in kesko); `on_non_numeric`
  is only required for `within`, so its absence is valid. Amounts are numeric
  strings.
- The LLM set `left:"statement"`, `right:"transactions"`, so `only_left`=only
  statement (PI-102), `only_right`=only transactions (PI-104) — matches the
  data; all four relations present.
- A sheet with an uncalculated formula in a BLANK-HEADER column is still not
  caught (pre-existing edge: blank-header detection uses `data_only=True`
  values, which are None for formula cells). Named columns are the modelled
  path; out of scope for v0.4.
- `pipeline.workspaces()` still auto-lists `data/_derived/` (one-level glob) as
  a dead workspace for the STANDALONE `modeller/app.py` (no top-level `*.json`,
  only `<ws>/` subdirs → harmless, not visible in the supervisor). Filtering it
  would touch `pipeline.py` (out of scope).
- `define.ask` remains a 4th local copy of the generate-form ask (factoring
  touches modeller/+fleet/; deferred).
