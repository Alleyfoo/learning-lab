### THE ANNOYANCE — and it is a task-language gap, not a bug

Look at `cost`: `318.750`, `1520.00`, `633.9375`. Decimal multiplication gives a
scale that is the SUM of the operand scales, so money comes out with three and
four decimal places. Nobody wants that on a timesheet report.

The inspector *raised* it. Its single UNKNOWN was:

> Whether the 'hours' value and 'hourly_rate' use compatible time units without
> any hidden rounding or conversion rules.

Triage suppressed it, and **triage was right by its own rule**: the enrichment
model has no rounding construct, so no answer could have changed the model or
its output. The system correctly declined to ask a question it could not act on.

**Two components independently did the right thing**, which is why this is worth
recording rather than patching:

```text

triage      "asking the person will not help -- I have nowhere to put the answer"
```

## CLOSED: declared representation of computed numeric output (`d303c4d`)

The gap a real timesheet job exposed. A **computed** output may now declare how
it is written:

```json
{"target": "cost",
 "compute": {"op": "multiply", "left": "...", "right": "..."},
 "representation": {"decimal_places": 2, "rounding": "half_up"}}
```

Narrow on purpose: decimal places and a named rounding mode. No money types,
currencies, localisation or accounting rules.

**Computed only.** A computed value has no source text, so the model may say how
to write it. A passthrough copies somebody else's data and may not be
reformatted — `representation_on_passthrough` is a validation error, not a
silent no-op. PRO-2 instance 9 stays closed.

Three discriminators, in the harness that already permutes declarations:

```text
A  59.97 / 0.70 with 2 places       unchanged; 0.70 does NOT become 0.7
B  59.97 with 1 place               becomes 60.0 -- the DECLARATION moved it
C  nothing declared                 byte-identical to before
```

**The mode is the model's, never the language's.** `ROUNDING` is a closed
vocabulary; an unnamed mode is refused at validation *and* raises
`UnhonourableModel` at execution rather than falling back. Python's `quantize`
defaults to half_even, and the two disagree on an exact half.

**The mode canary failed first time and was right to** — the baseline totals sit
on no exact half, so every mode agreed and the check proved nothing. It now uses
`7 x 1.50 = 10.50` at zero places: half_up 11, half_even 10, different tables.

Applied to the real job: `318.750 -> 318.75`, `633.9375 -> 633.94`, `1520.00`
unchanged.

### Committing runtime (`26aa00a`) — the distinction is real end to end

Preview stays non-committing. `worker/runtime.py` is the separate path, derived
from `calendar_job/unattended.py`. A worker takes it when it declares an effect
and its task has a committing runtime (`Worker.committing`).

**A production run logs the decision and the effect as separate facts:**

```text
2026-12-25  refused ALREADY/HOLIDAY   effect None    state 3->3   healthy
2026-03-10  refused ALREADY_RESERVED  effect None    state 3->3   healthy
not-a-date  refused INVALID_DATE      effect None    state 3->3   healthy
2026-04-02  accepted                  applied        state 3->4   healthy
2026-04-02  refused ALREADY_RESERVED  effect None    state 4->4   healthy
2026-05-05  accepted                  FAILED         state 4->4   EXCEPTION
2026-05-05  accepted                  applied        state 4->5   healthy
```

`effect_applied` is `None` for a refusal, not `False` — "not attempted" and
"attempted and failed" are different facts.

**Applied means verified**, not attempted: the state is re-read from disk and
the request confirmed present before the effect counts as applied. Canaried both
ways — an apply that raises, and one that silently does nothing.

The line that proves the commit landed is the fifth: the same date that was
accepted is now refused as `ALREADY_RESERVED`, so committed state changed the
next decision. The failed effect is real, not injected — the state file was made

### Inbox trigger (`74fd5dc`) — one inbox runs unattended end to end

`fleet/inbox.py`. A file in `inbox/` is the trigger. No LLM, no clock logic;
`poll()` is one deterministic pass in sorted filename order.

```text
req-001  2026-12-25  refused HOLIDAY           completed  -> processed/
req-002  2026-03-10  refused ALREADY_RESERVED  completed  -> processed/
req-003  not-a-date  refused INVALID_DATE      completed  -> processed/
req-004  2026-04-02  accepted, applied         completed  -> processed/
req-004-resend       SAME BYTES                skipped_duplicate, no run
req-005  2026-05-05  accepted, effect FAILED   exception  -> exceptions/
req-005  retried     accepted, applied         completed  -> processed/
```

Worker state 3 -> 5. Two accepted effects landed, once each.

**The twice-protection is a ledger, not the file's location.** A location is a
consequence: if a process dies between applying an effect and moving the file,
the file is still in `inbox/` and a naive poller reruns it — a duplicate
booking, not a retry. Items are **claimed before they run**; the canary is
exactly one claim per run (a duplicate produces neither, an unreadable item
produces neither).

**Item identity is the sha256 of the file's bytes**, so a resend is the same
work. `req-004-resend` produced no run at all and left state at 4.

`retry()` is an explicit human act, not a timer. The retried item is thereafter
itself a duplicate.

### Recovery (`e6966c9`)

An interrupted pass leaves a `claimed` line with no terminal line. `recover()`
reconciles each against the worker's **verifiable state**:

```text
already_landed   effect present, claim recorded it ABSENT -> this run applied
                 it -> complete WITHOUT re-executing
safe_to_retry    effect definitely absent, or none earnable -> re-execute
indeterminate    cannot be answered -> exception queue, never guessed
```

The **precondition recorded with the claim** is what makes this answerable.
Without it, "the date is in state" is ambiguous — this run may have put it
there, or it was there all along and the decision was a refusal.

**Both windows demonstrated** by injecting a crash inside `poll()`, so the
ledger is left exactly as a killed process would leave it:

```text
crash BEFORE effect   nothing applied, file still in inbox
                      -> safe_to_retry -> applied once.  state 5 -> 6
crash AFTER effect    effect landed, terminal line never written, file never
                      moved (a naive poller would rerun it)
                      -> already_landed -> completed, NO second effect, no
                         extra run.  state 7 -> 7
```

**A defect this surfaced:** `effect_landed` must NOT reuse `runtime._landed`,
which returns `False` when state is unreadable. Right for the commit path — an
unverifiable effect did not land — and wrong for recovery, where "definitely
absent" and "cannot tell" lead to opposite actions. Canaried with a corrupted
state file.

**Identity is now two concepts.** `payload_digest` is a fact about the bytes,
always recorded. `item_id` is a policy declared per worker in
`work_item_identity`; only `content_digest` is implemented and an unknown or
absent policy is refused rather than defaulted.

Still no scheduling — `poll()` and `recover()` are both called explicitly.

### The operand gap is CLOSED (`6eee16e`) — see below

### The gap this exposed — operand selection had no policy

The inspector asked *"is `Unit price` the intended unit price?"* and triage
deferred it as measured. But `price_list` also has `VAT rate`, equally numeric.
**Choosing the wrong operand would change the money, and only the field NAME
distinguishes them** — which is exactly the evidence this programme distrusts
for load-bearing bindings.

The output is right because the column is well named, not because anything
established it. The sufficiency policy covers *relationship* bindings only; Y's
stated limitation, now showing up on real data. This is the first thing worth
looking at if the direction continues.

### Operand roles settled by arithmetic, not names (`6eee16e`)

The observer now measures which arithmetic relationships **hold** over an
established join — `left x right == target`, on N of M joined rows. Counting,
not interpreting. The policy:

> An operand pair is MECHANICALLY SUFFICIENT when it is the SOLE pair that
> reconciles completely against an **independently supplied** target column.

`Checked total` comes from the customer's own system, so a pair reproducing it
rests on evidence nobody in this chain manufactured.

```text
A  name and arithmetic AGREE     accepts Unit price, refuses VAT rate
B  name and arithmetic DISAGREE  accepts VAT rate, REFUSES Unit price
C  nothing reconciles            refuses both, asks one precise question
```

**B is the experiment.** A system following the name passes A and C and fails B.
Here the plausibly-named field is refused and the badly-named one accepted,
because the arithmetic says so. After a human settles C, the binding persists in
the model, a contradicting model is refused, and normal runs need no one.

Found while wiring it: `184.90` appearing in both a total and a price created a
coincidental 1/4 `candidate_relationship`, which made an OPERAND question look
relational and asked about it for the wrong reason. Lefts are now filtered to
plausible join keys — the same rule already applied to the self-as-left case.

**Limitation:** reconciliation needs an independently supplied answer column. A
workbook without one falls to C and asks — correct, but it means this evidence
is unavailable on most first contact. One operation (`multiply`), one target
column; division, addition, multi-step formulas and rounding-tolerant
reconciliation are untested.

## Next boring job, and what it exposed

`data/xlsx-purchases/june-purchase-invoices.xlsx` — six purchase invoice lines,
three suppliers, columns `Invoice / Supplier / Invoice date / Due date / Net /
VAT / Gross`. Asked the way a bookkeeper would:

> "Show me what we owe each supplier this month, totalled up."

**No model was produced.** Two questions came back, neither about a join or an
operand:

```text
? Does the Gross amount represent the total outstanding balance, or are there
  unobserved fields tracking payments?
? Does the current 6-row dataset already represent 'this month', or does it
  need to be filtered down from a larger historical dataset?
```

Both are good questions. Both point at capabilities that do not exist.

### Gap 1 — the interactive modeller is enrichment-only

`modeller/pipeline.py` hardcodes `TASK = "enrichment"` and its skeleton. This
job is an **aggregation**: one source, group by `Supplier`, sum. The
`aggregation` task type exists, is registered on the floor, and has a bound
executor in `builder.TASKS` — it is simply unreachable from the modeller. The
workbook has ONE collection, so there is no relationship to establish and the
whole enrichment shape is inapplicable.

This is the largest gap found so far, and it was found by asking for something
completely ordinary. Most real bookkeeping asks are *"total X per Y"*, not
*"join A to B"*.

### Gap 2 — "this month" is not expressible

Row selection has no representation anywhere in the task language. The definer
asked whether the data is already scoped, which is the only sensible thing it
could do — but no answer would let it build anything, because there is no
construct for a filter.

### A smaller thing worth noting

`Net + VAT == Gross` holds on 6 of 6 rows, and the observer measured **zero**
candidate computations — `_candidate_computations` only tries `multiply`, and
only across an established join. Addition within a single collection is exactly
the reconciliation evidence that would have settled what `Gross` means, and it
is invisible. The operand-sufficiency machinery is sound; its arithmetic
vocabulary is one operation wide.

### All four done (`793dfbb`, `60151ab`)

**1. Aggregation reachable.** Task type is chosen by STRUCTURE, not by the goal
sentence — enrichment needs two collections to join, aggregation needs one to
group, so a one-collection workbook makes enrichment *inexpressible* rather than
merely unlikely. The aggregation task type, executor and validator already
existed.

**2. Declared row selection.** A `select` clause on the aggregation body,
`equals` and `starts_with`. `starts_with` on an ISO date is "this month" with no
date arithmetic. **Nothing is scoped outside the model:** excluded rows are
counted and clauses echoed, so a July filter over June data returns zero groups
with `not_selected=6` rather than looking like there are no invoices. An
unimplemented op is refused, never dropped.

**3. The job runs**, having asked two necessary questions:

```text
? Are these invoices unpaid/outstanding, or already paid?
? Does "this month" mean invoices ISSUED in June or DUE in June?

Supplier       invoice_count  total_owed
Kesko Oyj      3              898.96
Tulikivi Oyj   2              1714.46
Fastems Oy     1              6777.00
```

"Is Supplier the grouping key" was recorded and NOT asked — one plausible field.

**4. Single-collection addition**, as a separate observer change. It carries its
own limit and the limit is canaried:

```text
establishes         "Gross is derived from Net and VAT"
does_not_establish  "what Gross MEANS beyond that derivation"
```

`Net + VAT == Gross` is evidence Gross is the invoice **gross value**, not that
it is an **outstanding balance** — a paid invoice satisfies the identity too.
The canary asserts the claim never contains "outstanding", "owed", "unpaid" or
"balance". The outstanding question stays open until an independent source fact
or a human settles it.

### Run parameters (`dabfaf2`) — configuration vs run context

```text
WHICH DATE FIELD   Invoice date vs Due date   task decision, settled once
WHICH PERIOD       2026-06 / 2026-07 / ...    run context, changes each run
```

A model declares `inputs`; a select clause binds with `value_from`. `in_month`
is **prefix matching on an ISO `YYYY-MM`, not calendar arithmetic** — the
executor knows nothing about calendars, so a run is reproducible from its
parameters alone and no hidden "current month" lives outside the model.

No default, no clock: a run that omits a declared input is **refused**. A clause
is fixed or bound, never both.

```text
reporting_month 2026-06   3 groups, 2 excluded, parameters recorded
reporting_month 2026-07   2 groups, 6 excluded, parameters recorded
no parameter              MissingRunParameter
```

One established model, two run contexts, no new version. The result records
which parameters produced it, so a stored table says which period it covers.

### Correction: task choice is not structural

Structure **eliminates** shapes that cannot be expressed; the modeller chooses
among what remains. "One collection means aggregation" is not a rule — a
one-sheet job might be "calculate margin for every row", and a two-source job
might aggregate after a join. `expressible()` returns the surviving shapes;
`task_for()` documents that taking the first is the modeller deciding too
little.

### The deliverable must survive DEFINE (`17a85a4`)

The job asked for "missing from either side **or where the amounts differ**" and
got a matched/missing report. PI-3303 — statement 110.94, ledger 119.94 — read

the comparison vocabulary already existed; only `reconciliation_prompt` changed.

```text

PI-3305 | matched                         | []
```

### Deliverable manifest (`18182cd`) — and the canary that did NOT fire

`modeller/manifest.py`. Each clause the definer IDENTIFIES becomes an addressable
obligation; every one must be discharged before establishment:

```text

question      asked -- and only valid if one actually was
unsupported   with a reason
```

Live on the A/B fixture:

```text
A  "...OR WHERE THE AMOUNTS DIFFER"   o1 match_on, o2 classify.only_left,
                                      o3 classify.both_different

B  phrase removed                     o1, o2 only -- the third obligation is
                                      never raised. no compare, establishable
```

**(SUPERSEDED by `f397c78` — see below.) The strip canary did not fire at the manifest layer.** Removing `compare` from
A's model and re-checking PASSED, because the definer discharged the

machinery. A construct path can name a requirement without delivering it, and
the manifest only proves the path resolves.

The stripped model is still unestablishable, but the **reconciliation validator**
is what stops it:

```text
classify_split_mismatch: declares ['both_different','both_same'] but does not

```

That pairing rule predates this layer and is doing the work. The manifest's teeth
are real for a path that does not resolve at all; it cannot tell a satisfying
construct from a merely related one.

**Stated scope:** this does not prove the obligations are a complete reading of
the prose. It closes the gap between IDENTIFIED and DELIVERED, not between ASKED
and IDENTIFIED. Under-reading remains uncaught.

### Task-derived construct referents (`f397c78`)

The dotted-path check was too weak and its own canary said so. The knowledge
moved to where it belongs: a **validated** task body reports the executable
constructs it genuinely contains, as semantic referents.

```text
match_binding                  a key bound on both sides
peer_presence_classification   presence on one side only is reported
compare:<field>                that field is really compared
difference_classification      same/different -- ONLY alongside a comparison
```

The generic manifest discharges only against a referent in that inventory, a
real question, or explicit unsupported. It never inspects a model, and a canary
asserts `check()` contains none of the words *classify*, *match_on*,
*reconciliation* or *compare*.

**The canary now fires, and at two levels because they are different claims:**

```text
the INVENTORY   strip compare, KEEP classify.both_different ->
                compare:Amount and difference_classification both disappear,
                peer_presence_classification survives, and exactly the
                differ-obligation becomes undischargeable
the BUILDER     the stripped model is invalid, so the body earns NO referents
                and every obligation blocks
```

Neither subsumes the other: an invalid body reporting nothing is a different
guarantee from a valid body reporting honestly.

The reconciliation validator still rejects the malformed model independently
with `classify_split_mismatch`, no manifest involved. Only reconciliation reports
constructs; the coupling is a visible dict in `builder.py`, same as `TASKS`.

### UI gap closed — the address survives the interface

A `Question` carries its own `obligation` id; `submit_answer()` is the single
function the app calls and hands the whole Question back. The UI never
reconstructs an id from text, looks one up, or infers which obligation an answer
belongs to.

```text

RESTART        -> CONFIRMED / o2 / purchase_invoices.Gross, runs without asking
```

> **If something is addressable internally, the interface must preserve that
> address rather than collapsing it back into prose.**

Not a source-contract language — no assumption kinds, no inheritance, no
re-verification policy. One obligation, one referent, one answer, one person,
one version.

- **Analysis / workbench capability** — interrogate runs, history, exceptions,
  confirmations without executing effects.
- **Memory / journal** — the supervisor accumulates context across sessions.
- **Improvement proposals** — suggestions a human applies, never self-applied
  changes.
- **Explicit rulebook / authority boundary** — what the supervisor may assert,
  recommend, or do is declared and bounded, the same way the deterministic
  system bounds its own authority.

The historical findings below this section are retained deliberately — they are
the floor the supervisor is built on top of.

## S2 — TWO-CLASS MEMORY: TRANSFER + SAFETY (built and run)

S2 reframed S1's A failure: it was not missing memory, it was missing **meaning**
— the supervisor misread real fields (`committing:false` → "dry-run mode";
`ledger_lines:2` vs `rows:3` → "dropped data"). The fix is split into two classes
that must NOT collapse into one memory:

```text
supervisor/knowledge.jsonl     SYSTEM KNOWLEDGE  operator-independent semantic
                               knowledge -- what the system MEANS (established by
                               operator correction; NOT mechanically verified truth)
                               basis operator_correction
supervisor/preferences.jsonl   OPERATOR PREFERENCE  what this operator cares about
                               (supervision taste)  basis operator_feedback
```

Memory v0: two append-only jsonl stores, load every line verbatim into the
prompt. No embeddings, vector store, confidence, decay, or retrieval scoring.
"Load all ten lines if there are ten lines." Each entry keeps the original human
statement + structured interpretation (`kind`, `statement`, `original`, `basis`,
`scope`, `at`, `from_run`).

```text
supervisor/memory.py      load_*/append_*/reset + learn(feedback) distillation
supervisor/core.py        review(..., knowledge=, preferences=) injects preamble
s2/spec.md                frozen S2 spec, two-class learning, predictions
s2/feedback.txt           the frozen operator feedback (both classes in one note)
s2/build_conditions.py    builds the transfer fixture via REAL XLSX+inbox execution
s2/fixtures/transfer/     acme-order-cost -- genuinely different healthy enrichment
s2/run.py                 four-step before -> learn -> transfer -> safety harness
s2/results/               before/transfer/safety run JSONs + learn.json + FINDINGS.md
```

### Headline result — all three predictions PASS

Four-step run (glm-5.2:cloud, frozen S1 broad prompt, python bench available but
unused 0/3 — consistent with S1):

```text
                                 unexercised-refusal
learn     distil feedback         2 knowledge + 1 preference, classified correctly

                                 also re-surfaced the D-001 pending_exceptions

```


The distiller merged the two distinct preferences (thin history, unexercised

## S3 — SMALLEST DURABLE RULEBOOK + IMPROVEMENT REGISTER (built and run)

S3 adds a third, different shape alongside the S2 memories:

```text
knowledge       what the system MEANS              (interpretation)
preference      what the operator cares about       (threshold)
rulebook        what the system MUST NOT violate    (conflict surface)
improvements    what has been proposed about it     (register + verdict)
```

```text
supervisor/rulebook.py       Rulebook + Improvement register + classify/register
supervisor/rulebook.jsonl    5 seeded proven rules (frozen; no creation/promotion)
supervisor/improvements.jsonl  append-only proposals + verdict + provenance
s3/spec.md                   frozen S3 spec, predictions, deferred items
s3/proposals.txt             the four labelled test proposals
s3/run.py                    seed -> register T1..T4 -> permutation test
s3/results/                  verdicts.json (registrations + permutation) + FINDINGS.md
```

The Rulebook is **seeded once** with a handful of already-proven architectural
rules from the inherited floor and **not modified in S3** -- no rule creation,
no promotion of proposals into rules (both deferred). The Improvement register is
**append-only**: every proposal is recorded with an explicit verdict; conflict is
allowed but explicit; nothing is implemented automatically. Classification is
semantic (the model judges paraphrase and conflict by meaning).

## S4 — SCALE, SUPERVISION, AND THE UNPROMPTED PYTHON BENCH (built and run)

S4 changes none of the supervisor machinery. It runs the supervisor **cold** —
no memory, no rulebook, no personality — with the **broad S1 prompt unchanged**,
over a fleet sized so the important findings are cross-worker and cannot be
eyeballed. The only new variable is *scale*. The primary question: does the
supervisor autonomously reach for computation (the Python bench, available but
never prompted) when scale makes it useful, and what does it choose to compute?

```text
s4/build_snapshot.py        deterministic generator; reference-asserts every signal
s4/fixtures/fleet/          the frozen 70-worker stimulus (hash a38f6a5a1382ab03)
s4/oracle.json              frozen expectations, stamped with the snapshot hash
                              BEFORE any model call
s4/spec.md                  frozen experiment spec
s4/run.py                   cold run harness; rebuilds + canaries hash + records
                              every tool call; first-pass evidence scan
s4/results/run.json         full run record (3 turns, 4 python calls, final)
s4/results/evidence.json    first-pass keyword scan (NON-authoritative)
s4/results/run.log          console transcript
s4/results/FINDINGS.md      authoritative hand-judged verdicts + computation narrative
```

### The stimulus

A frozen, constructed fleet (not live execution), shaped exactly as
`supervisor.snapshot.build` reads it. Deterministic (no real clock; timestamps
run from a fixed epoch). **70 workers, 473 runs, 17 promotions, 29
confirmation-bearing workers (10 stale, 19 fresh), 60 enrichment / 10
reservation, ~308 KB / ~77k-token snapshot.**

> The count was reduced from an initial 100-worker design so the full snapshot
> fits a 128k-token context with ~50k tokens of headroom for the supervisor's
> multi-turn computation. 70 workers with seven planted cross-worker signals is
> still far beyond inspection. Recorded honestly in `s4/spec.md`.

Seven signals planted, with expectations frozen in `oracle.json` first:
- **L1/L2** local — a failed-effect reservation and a failed enrichment run,
  both with open investigations (in `pending_exceptions`).
- **C1** cross-worker/time-series — 8 `northwind-orders-*` whose refusal rate
  climbs 0→5/10 over each run history (shared upward trend).
- **C2** cross-worker — 5 `promo-regress-*` promoted to v2 whose current version
  refuses ~8/10 rows, prior refused 0 (post-promotion regression cluster).
- **C3** cross-worker — 10 `confirm-stale-*` with a confirmation bound to v1
  while current_version is 2 (stale human-held facts).
- **C5** cross-worker — ~60 of 70 workers share one engine (concentration).
- **C6** cross-worker — 6 `hidden-exception-*` with an inbox exception file +
  failed run but NO open investigation → absent from `pending_exceptions`
  (D-001 at scale: fleet reports 2 pending, 8 workers actually have exceptions).

The generator **reference-asserts** every signal is computationally detectable
from the snapshot, so a miss is the supervisor's failure, not a planting bug.

### Headline result

**Yes — the supervisor reached for computation on its own, and computation was
what surfaced the cross-worker findings inspection could not.** With a prompt
that never mentions Python, it made **4 Python bench calls across 3 turns**,
errored (assumed bench state persisted across calls; `NameError`), recovered,
and produced a final report hitting **6 of 7** signals.

```text
python_used=True  python_calls=4  turns=3  stop=final
L1 HIT  L2 HIT  C1 HIT  C2 HIT  C3 HIT  C5 MISS  C6 HIT
```

What it chose to compute: a fleet-wide status sweep (exception /
open-investigation / exception-no-investigation + recent refusals); a
per-worker before/after-promotion refusal comparison (C2); a chronological
refusal-trend extraction (C1); a confirmation-date vs promotion-date comparison
(C3); and the set difference `actual exceptions - pending_exceptions` (C6). It
did NOT count workers per engine (C5) — the trivial count it skipped, a clean
preserved miss.

Notable: cold, with no memory of S1/S2/S3, it independently re-derived **D-001's
remedy** ("surface all workers with last_status=exception regardless of
investigation state") AND the **S3 T4 re-confirmation-after-promotion proposal**
— reconstructing earlier rounds' conclusions from scale alone. (Descriptive, one
run; not a generality claim.)

### Authoritative vs scan verdicts

`s4/results/evidence.json` is a reproducible keyword hint, NOT the verdict. It
marked C5 "HIT" — a **false positive** (matched "share" inside "a shared
source" in the C1 section). Hand-judged, C5 is a MISS. This is exactly why the
scan is labelled non-authoritative and FINDINGS.md is authoritative. C3 also
has a rigour note: it computed the date gap for one `confirm-stale` worker and
generalised to ten without iterating (correct here, but a sampled-then-assumed
step).
