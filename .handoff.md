# Workspace v0.1 -> handoff (session 2026-08-17)

## What was completed

**Workspace v0.1: the Supervisor Dashboard is now the primary surface.** A
completed supervision run produces and persists a human-facing *current
assessment* -- findings, priorities, normal/no-action context, and suggestions --
shown on the Dashboard the moment the app opens. Machine-state counters are
demoted to a small secondary strip; the raw snapshot and per-run evidence moved
to a "Fleet & run details" tab. Flow is no longer a separate page -- the Review
action lives on the Dashboard and its output IS the dashboard.

This was built on top of Workspace v0 (the harness + backlog + routing + 4-tab
app, already shipped). The user-confirmed design decision: **the supervisor
files the assessment itself** via a `file_assessment(findings, priorities,
normal_context)` tool (same pattern as `raise_proposal`), rather than the
assessment being derived post-hoc. The model authors the three judgment fields;
the fourth -- suggestions -- is the set of proposals it raised in the run (no
duplication, one path into the backlog).

### New / changed files

- `supervisor/assessment.py` (NEW) -- the assessment artifact

  Backward-compatible (`extra_inject=None` is the default). `--self-test`

  `runs/<run_id>/assessment.json`), adding `session["assessment"]`. `PROMPT`

  asserts the assessment is composed with the filed fields + the proposal as a
  suggestion + persisted).
- `supervisor/app.py` (REWRITTEN tab structure) -- tabs are now **Dashboard /
  Improvements / Rules / Fleet & run details**. Dashboard: the Review-fleet
  action + a secondary counter strip + the current assessment (normal_context
  first -- the anti-Quiet-Monday anchor -- then findings, priorities,
  suggestions with a pointer to Improvements, narrative expander, run caption).
  Improvements/Rules unchanged. Fleet & run details: raw snapshot JSON + full
  counters + the last run's per-turn evidence.
- `run-supervisor.bat` (NEW) -- launch helper (`python -m streamlit run
  supervisor/app.py` from the project root) since `streamlit` is not on PATH.

### The assessment artifact

```python
{
  "schema": "supervisor.assessment/v1",
  "run_id", "at", "snapshot_hash", "fleet_shape",
  "filed": {"findings": [str], "priorities": [str], "normal_context": str} | None,
  "suggestions": [{"id": "IMP-NNN", "text": str, "evidence": str}],  # the run's raised proposals
  "final_response": str | None,                                     # the model's final prose
  "model", "stop_reason", "turn_count", "elapsed_seconds"
}
```

Persistence: `supervisor/current_assessment.json` (current, overwritten each run
-- the Dashboard's source of truth on load) + `supervisor/runs/<run_id>/
assessment.json` (per-run copy).

## Known issues / caveats

- **The model must call `file_assessment` for a structured dashboard.** If it
  never calls it (e.g. it runs to max_turns, or just writes prose), `filed` is
  None and the Dashboard shows a "supervisor did not file a structured
  assessment" warning + the final-response narrative + the raised proposals as
  suggestions. Graceful, never a crash. Whether glm-5.2:cloud reliably calls
  `file_assessment` with the right shape has NOT been exercised against the real
  model yet (only the stub model in the self-test). The real-model check is the
  next step.
- **Fleet & run details per-turn evidence is in-memory only.** It shows the last
  run from the current Streamlit session (`session_state["last_session"]`); on a
  fresh app open (no Review yet) it is empty with a note. The persisted
  `runs/<run_id>/run.json` + `session.jsonl` hold it but are not browsed (the user
  explicitly deferred the past-run browser). The Dashboard itself works from the
  persisted `current_assessment.json`, so it survives restarts.
- **max_turns bumped to 8** for the app's Review call (was 6) since filing the
  assessment is one more act; the model can batch multiple `raise_proposal` /
  `file_assessment` calls in one python block, as the real e2e already did with
  5 proposals in 4 turns.
