# v0.6 — Recurring source identity (design note, no code)

Status: design only. No implementation in this note. No connector work, no
materialization archive, no filename-pattern authority. Written against the two
real workers in the repo: `fazerish-invoicing` (operational XLSX inbox) and
`acme-august-recon` (v0.4 anchored). Investigation findings are summarised in
memory `v06-recurring-source-investigation`; this is the design.

## 1. The problem

v0.4/v0.5 can take an unfamiliar workbook, understand it, establish work, and
give that work a destination. But a real company does not send `August.xlsx`
once. It sends August, September, October… The architectural question:

> When does a new file represent new work for an **existing model**, rather than
> a new thing that needs modelling?

v0.4 provenance answers "what workbook did we use when we **established** this?"
Recurring operation needs to answer "what exact workbook produced **this
particular run**?" Those are different truths.

## 2. The four objects

| object | meaning | acme-august today | fazerish today |
|---|---|---|---|
| SOURCE DEFINITION | what kind of business input this is (the contract a recurring arrival must satisfy) | on the **model** as `sources[...].origin` (founding instance shape); not forward, not re-invokable | split: shape on **identity** `adapter_sheets`, executable path on model `sources`; no `origin` |
| SOURCE INSTANCE | the actual file/dataset received this time | **missing** — anchored to one fixed `_derived/*.json` | partial — ledger has `file`+`payload_digest`; materialized JSON overwritten each poll |
| MATERIALIZATION | the deterministic machine representation made from an instance | operational at establish only; not re-invokable | operational per poll; provenance-light (`_note` only) |
| RUN | the work performed using that representation | never run; run-record format exists but ties a run to a **model version only** | runs; `runs.jsonl` has outcome but **no link to the input file** |

The reusable machinery (already built, shared by both paths): the single
converter `adapters/xlsx.py:convert` (+ `write_collections`, `SheetSpec`), which
already validates an arrival against a declared shape (sheet exists, header row
present/non-blank/non-duplicate, no uncalculated formulas) and **refuses with
named problems on mismatch** — exception ledger, file to `exceptions/`, no run.
That is exactly the "REFUSE / source shape changed" behaviour v0.6 needs. The
inbox loop `convert → write-to-model-source-paths → record_run`
(`fleet/inbox.py:273-300`) is the recurring loop, minus run-level provenance.

## 3. Corrected placement: stable source ROLES vs version-bound executable input CONTRACTS

An earlier draft proposed putting the whole "source definition" on identity.
That is wrong, and the correction is the spine of this design.

There are two different things muddled together as "source definition":

- A **source role** is the stable *business* identity of an input stream:
  "the supplier statement", "the ledger transactions". It is stable
  across model versions, across periods, and across shape changes. It survives
  a re-model. It belongs on **identity** (`worker.json`), alongside `customer`
  and `destination` — a version-less business fact.

- An **executable input contract** is the *shape* an arrival must have to be
  accepted by **this model version**: which sheet, which header row, which
  collection it maps to. It is **version-bound**: the task semantics in v1 were
  built against a specific input shape; if the source shape changes you either
  refuse (the existing behaviour) or re-model, producing v2 with a **new
  contract**.

### 3.0 Version-bound does NOT mean "inside `v1.json`" — a separate versioned file

The first instinct — put the contract on the model version — is right about
*versioning* but wrong about *the file*. `taskmodel.parse()` (taskmodel/
`task_model.py:191-197`) treats **every unknown top-level key as part of the
task-specific `body`**: `known = {"model_version","model_id","task","sources"}`
and `body = {k:v for k,v in raw.items() if k not in known and not k.startswith("_")}`.
So an `input_contract` key added to `v1.json` would mechanically become part of
reconciliation/enrichment task semantics and be handed to the task's body
validator — exactly the contamination we are trying to avoid. (This is the same
reason v0.4's `materialization.json` uses a `_note` key: `_`-prefixed keys are
excluded from `body`. A `_input_contract` hack would compile but would smear an
ingress concern into a task file by convention, not by right.)

The clean placement is a **separate versioned file** alongside the model, with
the same version number, advancing together (initially required to):

```
worker identity (worker.json)        → stable source roles
versions/v1.json                     → task semantics (what to do)
input_contracts/v1.json              → accepted input representation (what data
                                        this version may do it with)
```

A run records **both** version numbers (`model=v1`, `input_contract=v1`). They
are two different versioned truths. The rule:

> **A model answers what to do. An input contract answers what data
> representation this version is allowed to do it with.**

They can be required to advance together for v0.6 (a re-model produces a new
model version AND a new contract version, same number); decoupling them is a
later decision, not v0.6.

The resulting architecture, end to end:

```text
WORKER IDENTITY
supplier statement
ledger transactions
        │
        │ stable roles
        ▼
INPUT CONTRACT v1
Statement / header 3
Transactions / header 2
        │
        │ validates
        ▼
INPUT SET
statement instance A
transactions instance B
        │
        │ complete
        ▼
TASK MODEL v1
reconciliation semantics
        │
        ▼
RUN
model=v1
input_contract=v1
input_set=X
exact source digests...
```

Putting a version-bound contract on *identity* is still the category mistake the
first draft made (identity is version-less and holds only stable facts). The
separate-file placement keeps identity clean AND keeps task semantics pure.
**Fazerish's `adapter_sheets` shape (sheet/header_row/collection) currently lives
on identity — that is the mistake in the existing code; v0.6 moves that shape
into `input_contracts/v1.json`.** Acme's `origin` stays in `versions/v1.json`
(correctly, as founding provenance); v0.6 adds `input_contracts/v1.json` beside
it and adds the stable role set to acme's identity so the recurring path can
see it.

`origin` and the contract are related but distinct:
- `origin` = provenance of the **founding** instance (which specific workbook
  established this version). Historical. Lives in `versions/v1.json`.
- contract = the shape **future** instances must match to be accepted by this
  version. Forward. Lives in `input_contracts/v1.json`.

They share `sheet`/`header_row` at establish (the founding instance's shape
becomes the first contract) and diverge thereafter. At a re-model, the contract
version advances; `origin` is re-stamped to the new founding instance.

### 3.1 What stays, what moves — per worker

**`fazerish-invoicing`** (converge onto the corrected split):
- identity keeps the **stable** parts of today's `adapter_sheets`: the role set
  (`order_lines`, `price_list`), their stable business names, that they are both
  filled by one **shared** workbook, `input_adapter: "xlsx"`,
  `work_item_identity: "content_digest"`.
- identity **loses** the shape (sheet/header_row/collection) — that moves into
  `input_contracts/v1.json` as the executable input contract.
- `input_contracts/v1.json` gains: per role, the contract
  `{sheet, header_row, collection}` (today spread across `adapter_sheets` +
  `sources`). `versions/v1.json` keeps `sources` (executable paths) and may gain
  an `origin` for fazerish's own founding instance (it has none today; v0.6 may
  add one so fazerish and acme share one provenance shape).

**`acme-august-recon`** (gain the operational shape without losing v0.4 origin):
- identity **gains** the stable role set: `statement` ("supplier statement"),
  `transactions` ("ledger transactions"), both **sole** slots (each is its own
  workbook), both required, `input_adapter: "xlsx"`,
  `work_item_identity: "content_digest"`. This is what unblocks the recurring
  path — today acme has none of it and September exceptions out before
  conversion.
- `input_contracts/v1.json` gains the forward contract per role, same shape at
  establish (`statement`: sheet `Statement`, header_row 3; `transactions`: sheet
  `Transactions`, header_row 2). `versions/v1.json` keeps `origin` (founding
  provenance) unchanged. The contract is the forward view; `origin` stays the
  historical pointer.

The inbox path's spec source shifts from `w.identity["adapter_sheets"]` to the
current `input_contracts/v<N>.json`. That is the one mechanical shift implied by
the correction (not implemented here).

## 4. Document slots and bindings

A **slot** is a role-shaped hole in a complete input set. A **binding** assigns
an arriving document to a slot, validated against that slot's contract.

- **slot kind** — `sole`: this slot is filled by its own whole document (acme:
  `statement` ← one supplier-statement workbook; `transactions` ← one ledger
  workbook). `shared`: this slot is one sheet within a document that also fills
  other slots (fazerish: `order_lines` ← `Order lines` sheet and `price_list` ←
  `Price list` sheet, both in one workbook).
- **binding authority** — an arriving document is bound to a slot by an
  **explicit operator act** (the operator says "this is the next supplier
  statement"), or trivially for single-shared-document workers. **The filename
  is never the authority.** `supplier_september.xlsx`, `stmt.xlsx`, or
  `untitled.xlsx` are all acceptable as the `statement` instance if the operator
  binds it there and the adapter validates its shape against the contract. The
  filename and digest are **provenance**, not the grounds for the binding.
- **validation** — once bound, the document is run through the existing
  `adapters/xlsx.py:convert` against that slot's contract (sheet/header_row). A
  mismatch is a named refusal → the binding fails, the document is exceptioned,
  no run. This is the existing refusal machinery, applied per-slot.

Illustrative role set on identity (acme):

```
source_roles:
  statement:    {label: "supplier statement", slot: sole, required: true}
  transactions: {label: "ledger transactions",        slot: sole, required: true}
input_adapter: xlsx
work_item_identity: content_digest
```

Illustrative per-role contract on the model version (acme v1):

```
input_contract:
  statement:    {sheet: Statement,    header_row: 3, collection: statement}
  transactions: {sheet: Transactions, header_row: 2, collection: transactions}
sources:        # executable bindings, unchanged shape
  statement:    {path: _derived/acme-august/statement.json,    origin: {…founding…}}
  transactions: {path: _derived/acme-august/transactions.json, origin: {…founding…}}
```

## 5. Complete multi-document input sets

An **input set** is the collection of bindings that will feed one run. It is
**complete** when every required slot is bound; until then it is partial and
**staged**.

- **fazerish** — one shared workbook binds both `order_lines` and `price_list`
  at once. Input set is complete on the first (only) arrival. This is the
  existing per-file run, recast as "one document completes a 2-slot set."
- **acme-august** — two sole slots, two documents. `supplier_sept.xlsx` arrives
  → bound to `statement` → validated → materialized into the `statement`
  collection path → input set is **partial (1/2)**, staged. Later
  `ledger_sept.xlsx` arrives → bound to `transactions` → validated →
  materialized → input set **complete (2/2)** → run fires.

Completeness is N-of-M over required slots. The staging area (the partial input
set with its bindings and the materialized collections already written) is a new
first-class object that persists between arrivals. A run fires **only** when the
set is complete — a reconciliation cannot run on one side.

### 5.1 The input set needs identity, not just slots

Binding a file to `statement` alone does not say *which set* it belongs to.
Consider two partial sets in flight:

```
September statement  waiting for September ledger
October statement    waiting for October ledger
```

Binding an arriving `statement` document to the `statement` slot is ambiguous
between the two sets. We must not infer the set from month or filename — that
would re-introduce filename-as-authority through the back door. So an input set
needs an explicit identity.

For v0.6 the narrow choice is: **one open input set per worker.** A worker has
at most one staged (partial or complete) set at a time; binding a `statement`
fills the `statement` slot of *that* set. This is an explicit limitation — it
rules out overlapping periods in flight — and it is stated as such, not left
undefined. A future version may introduce an operator- or system-generated
`input_set_id` to allow several sets in flight; the run record carries
`input_set` so either choice is forward-compatible. The limitation is acceptable
because the September-Acme probe and the realistic near-term operation are
one-period-at-a-time.

This generalizes the current per-file run to arbitrary slot counts and
document/slot fan-in, without changing the converter or the engine.

## 6. The minimal run-input provenance record

When a run fires from a complete input set, the run record (`runs.jsonl`)
records, per slot, which instance filled it, plus the versions that governed the
run. This is the SOURCE-INSTANCE → RUN link — the genuinely new object. Minimal
shape:

```
run_input:
  input_set:      <the worker's open input set identity>
  input_contract: 1           # the input_contracts/v<N>.json that validated
  model:          1           # the versions/v<N>.json that ran
  slots:
    statement:
      {document: supplier_sept.xlsx,
       digest: <sha256 of bytes>,
       sheet: Statement,
       header_row: 3,
       materialized_as: _derived/acme-august/statement.json}
    transactions:
      {document: ledger_sept.xlsx,
       digest: <sha256 of bytes>,
       sheet: Transactions,
       header_row: 2,
       materialized_as: _derived/acme-august/transactions.json}
```

- The run record already carries `{at, version, ok, rows, refused, problems}`;
  `run_input` is one new field alongside them. (The existing `version` is the
  *model* version; `run_input.model` restates it alongside `input_contract` for
  one-place readability — they advance together in v0.6.)

### 6.1 `run_input` is written atomically with the run record

`fleet.record_run()` (fleet/`fleet.py:249-294`) constructs the record and
appends the immutable `runs.jsonl` line at line 292 **before returning**. The
record is assembled in three branches (committing / reservation / else) and then
a single `_append`. We cannot append the run and decorate it afterwards — the
line is immutable once written, and there is no run ID to join on.

So `run_input` is passed **into** `record_run`:

```
record_run(w, request=None, run_input=<the provenance block above>)
```

and merged into `record` before the single append. This is much narrower than
introducing a separate append-only linkage record with a real run ID, which v0.6
does not need. (A run ID + separate linkage record is a later option if runs and
provenance ever need to advance independently; not now.)

### 6.2 Digest identifies bytes; it does not preserve them

The first draft said "digest → exact bytes." Strictly, SHA-256 tells us whether
some bytes are the *same* bytes; it does not let us reconstruct them. So the
truthful claim is:

> **A run identifies the exact source content by digest.** "Show me the exact
> source used in this run" is only truthfully answerable if the raw arrivals are
> durably retained and retrievable by that digest.

Today `fleet/inbox.py:315` moves processed files to `processed/<path.name>` —
the **bare filename** — so two arrivals with the same name (e.g. two
`statement.xlsx` from different months) collide and the second overwrites the
first's raw bytes. The ledger keeps `file` + `payload_digest`, so the digest
distinguishes them on the ledger, but the first raw file is gone from
`processed/`.

v0.6 therefore requires **collision-safe raw retention**: retained source
instances are stored by digest (or by a digest-namespaced name), not by bare
filename, so "show me the exact source used in run R" resolves to
`run → slot → digest → retained raw file`. This is NOT a materialization archive
(the materialized JSON is still overwritten per run); it is retaining the *raw
arrival* the digest already commits to. With that, the full chain is truthful:
worker → run → slot → digest → retained raw bytes, and `materialized_as` names
the representation that was current at that run.

## 7. The recurring flow (sequence, no code)

1. A document arrives in the worker's inbox (or is dropped via the v0.5 inbox
   panel).
2. The operator **binds** it to a slot/role of the worker's open input set
   (explicit act; or trivially implied for single-shared-document workers).
   Filename is not consulted for authority.
3. The adapter **validates** the bound document against that slot's contract in
   the current `input_contracts/v<N>.json` — the existing `convert` refusal
   path.
4. On success, **materialize** into the collection path the model declares
   (`sources[role].path`) — the existing `write_collections`. The materialized
   JSON is overwritten (no archive); the raw arrival's digest is captured.
5. The binding is recorded in the **staged input set**. If the set is now
   **complete**, proceed to 6; otherwise stop and wait for the remaining slots.
6. **Run** the worker over the complete set, passing the assembled `run_input`
   (versions + per-slot instance/digest/sheet/header_row/materialized_as) INTO
   `record_run(..., run_input=...)` so it is written **atomically** with the run
   record — one immutable `runs.jsonl` line (§6.1).
7. **Retain the raw arrival collision-safe** — by digest, not bare filename
   (§6.2) — so the digest the run records can be retrieved later.
8. Terminal ledger + move to `processed/` (namespaced), as today.

On a shape mismatch at step 3: refuse → exception ledger → file to `exceptions/`
→ **no run**, no partial state mutation for that slot. The operator may then
choose **"re-model source"** as a separate, explicit action (new model version
+ new `input_contracts` version, new founding `origin`). The system never
reasons "looks vaguely like September, probably the same thing" — that would
undo the deterministic
boundary the converter enforces.

## 8. Explicitly NOT in v0.6

- **No filename pattern as authority.** Bindings are operator acts + shape
  validation. No `supplier_*.xlsx` globbing decides what a file is, and no
  month/filename inference decides which input set a binding belongs to.
- **No contract inside `versions/v1.json`.** The contract lives in its own
  `input_contracts/v<N>.json` so `taskmodel.parse` cannot smear ingress concerns
  into task `body` (§3.0). A `_`-prefixed-key hack is declined for the same
  reason.
- **No separate run/linkage record.** `run_input` is a kwarg to `record_run`,
  written atomically with the run line (§6.1). No run ID, no second append-only
  file. (A run ID + decoupled linkage is a later option, not v0.6.)
- **No multiple input sets in flight.** v0.6 allows one open input set per
  worker (§5.1). An `input_set_id` for overlapping periods is a later option;
  the run record carries `input_set` so either is forward-compatible.
- **No connector work.** Destinations stay v0.5 declared intent. v0.6 is about
  input recurrence, not output delivery.
- **No materialization archive.** Materialized JSON is overwritten per run;
  provenance lives on the run record. What IS retained collision-safe is the
  **raw arrival** (by digest), so the digest's claim is truthful (§6.2) — that
  is raw retention, not a materialization archive.
- **No decoupled version advancement.** Model version and input-contract
  version advance together (same number) in v0.6.
- **No implementation yet.** This note is the design. The reusable mechanics
  (converter, validation/refusal, materialize-to-source-paths, run engine) are
  not in doubt; the design work is the role/contract split (separate file), the
  multi-document input set with identity, and the atomic run-input record.

## 9. Acceptance probe (the simple real-world test)

Take the Acme August reconciliation already established. Create a September
version of `supplier.xlsx` (Statement sheet, header row 3) and `ledger.xlsx`
(Transactions sheet, header row 2). Without invoking the modeller:

- bind `supplier_sept.xlsx` → `statement` → validate against
  `input_contracts/v1.json` → materialize → input set partial (1/2);
- bind `ledger_sept.xlsx` → `transactions` → validate → materialize → input set
  complete (2/2) → run;
- the run record (one atomic `runs.jsonl` line) carries `model=v1`,
  `input_contract=v1`, `input_set=<X>`, and per slot
  document/digest/sheet/header_row/materialized_as;
- the raw arrivals are retained by digest, so "show me the exact source used in
  this run" resolves to worker → run → slot → digest → retained raw bytes.

Then a shape-changed October statement (header moved to row 4) → binding fails
at validation → exception, no run → operator may choose to re-model as a
separate explicit action (new model version + new `input_contracts` version).

This probe exercises exactly the four boundary decisions — separate contract
file, atomic run-input, one open input set, digest-truthful raw retention —
plus the role/contract split and multi-document completeness, over existing
machinery.
